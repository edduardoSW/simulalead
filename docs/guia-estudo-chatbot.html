Guia de estudo

Entendendo o código do chatbot

Este material organiza a parte do chatbot do projeto Leads EJ para facilitar sua compreensão: onde fica a interface, onde a resposta é gerada, como a persona do lead é montada e como o fluxo completo funciona.

1. Visão Geral

O chatbot não está concentrado em um único arquivo. Ele é formado por uma tela React, uma rota de API e dados que descrevem o lead.

Resumo em uma frase: o frontend captura a mensagem do vendedor, envia para /api/simulate, a API monta uma persona de lead e devolve uma resposta gerada pelo Gemini ou por um fallback local.

2. Arquitetura

Parte Arquivo Responsabilidade
Tela da simulação web/components/GeminiSimulation.tsx Mostra o chat, guarda mensagens, recebe input e chama a API.
API do chatbot web/app/api/simulate/route.ts Valida a conversa, monta o prompt/persona e gera a resposta.
Caixa de entrada local web/components/LocalConversations.tsx Usa a mesma API em um formato de conversa assíncrona.
Dados dos leads web/lib/leads.ts Define perfil, dificuldade, objeções e condições de reunião.

3. Fluxo Da Mensagem

1O usuário digita uma abordagem no campo de texto.
2send() pega o texto, limpa o input e adiciona a mensagem no histórico local.
3O frontend chama /api/simulate com lead, scenario e messages.
4A API valida os dados e decide se usa Gemini ou resposta local de fallback.
5A API monta a persona do lead e envia o histórico para o modelo.
6A resposta volta para o frontend e aparece no chat como mensagem do lead.

Caminho mental

Usuario
  -> GeminiSimulation.tsx
  -> /api/simulate
  -> Gemini API
  -> /api/simulate
  -> Tela do chat

4. Tela Principal Do Chat

Arquivo: web/components/GeminiSimulation.tsx

Esse componente controla a simulação direta. Ele guarda o histórico, o texto digitado, o estado de carregamento e possíveis erros. 

const [messages, setMessages] = useState<Message[]>([]);
const [input, setInput] = useState("");
const [thinking, setThinking] = useState(false);
const [error, setError] = useState("");

O que cada estado significa

  • messages: lista de mensagens exibidas no chat.
  • input: texto que ainda está no campo de digitação.
  • thinking: indica que o lead está "pensando".
  • error: guarda erro de API ou conexão.

A função mais importante: send()

async function send() {
  const text = input.trim();
  if (!text || thinking) return;

  const nextMessages = [...messages, { from: "seller", text }];

  setMessages(nextMessages);
  setInput("");
  setError("");
  setThinking(true);

  const response = await fetch("/api/simulate", {
    method: "POST",
    headers: { "Content-Type": "application/json" },
    body: JSON.stringify({ lead, scenario, messages: nextMessages })
  });

  const data = await response.json();
  setMessages((current) => [...current, { from: "lead", text: data.text }]);
}
Como estudar este arquivo: primeiro entenda os estados, depois leia send() de cima para baixo, e por fim olhe o JSX para ver como cada estado aparece na interface.

5. API De Simulação

Arquivo: web/app/api/simulate/route.ts

Essa rota é o cérebro do chatbot. Ela recebe a conversa, valida os dados, monta o comportamento do lead e retorna a resposta. 

export async function POST(request: Request) {
  const apiKey = process.env.GEMINI_API_KEY;
  const body = await request.json();

  if (!body.lead || !Array.isArray(body.messages) || body.messages.length === 0) {
    return Response.json({ error: "Conversa invalida." }, { status: 400 });
  }
}

Fallback local

Se não existir GEMINI_API_KEY, o sistema não chama o Gemini. Em vez disso, usa buildFallbackReply(). 

if (!apiKey) {
  return Response.json({
    text: buildFallbackReply(body.lead, body.messages),
    model: "local-persona-fallback",
    degraded: true
  });
}

O fallback observa a última mensagem do vendedor. Se encontrar termos como preço, prazo, case ou cliente, devolve uma resposta coerente com esse assunto.

Regra contra reunião cedo demais

Existe uma regra específica para impedir que o vendedor tente marcar reunião logo no começo, antes de diagnosticar o problema. 

const attemptsEarlyMeeting =
  /\b(reuni[aã]o|agenda|call|hor[aá]rio)\b/i.test(lastSellerMessage);

if (attemptsEarlyMeeting && sellerMessages.length < 4) {
  return Response.json({
    text: "Antes de marcar, eu ainda queria entender melhor..."
  });
}

6. Persona Do Lead

A variável systemInstruction é onde o comportamento do lead é definido. Ela transforma os dados do lead em instruções para o modelo. 

const systemInstruction = `
Voce interpreta exclusivamente um lead ficticio em um treinamento comercial.
PERSONA ATUAL: ${initialContact?.name || lead.name}, ${lead.role}
CONTEXTO: problema atual: ${lead.problem}
Solucao potencial: ${lead.solution}
Objecao visivel: ${lead.visibleObjection}
Preocupacao oculta: ${lead.hiddenConcern}
DIFICULDADE: ${lead.difficulty}
`;

Regras importantes da persona

  • Não sair do personagem.
  • Não dizer que é IA, prompt, ficha ou simulação.
  • Responder como uma pessoa brasileira em contexto profissional.
  • Não revelar todas as objeções ao mesmo tempo.
  • Não aceitar reunião nas primeiras mensagens.
  • Responder primeiro à pergunta atual do vendedor.
  • Manter continuidade com o que já foi dito.
Ponto-chave: o chatbot parece um lead porque o prompt define limites, estilo, objeções, dificuldade e condições para avançar.

7. Envio Ao Gemini

Antes de chamar o modelo, o código converte o histórico da conversa para o formato esperado pela API. 

const contents = body.messages.slice(-24).map((message) => ({
  role: message.from === "seller" ? "user" : "model",
  parts: [{ text: message.text.slice(0, 4000) }],
}));
  • seller vira user.
  • lead vira model.
  • Apenas as últimas 24 mensagens são enviadas.
  • Cada mensagem é limitada a 4000 caracteres.

Depois disso, a API tenta chamar uma lista de modelos Gemini. Se houver falha temporária, ela tenta novamente ou usa fallback.

Esse componente usa a mesma rota /api/simulate, mas cria uma experiência de inbox. O vendedor pode escrever uma ou mais mensagens antes de realmente enviar ao lead.

Diferença principal: GeminiSimulation.tsx é conversa imediata. LocalConversations.tsx é conversa assíncrona, estilo caixa de entrada.

9. Dados Dos Leads

Arquivo: web/lib/leads.ts

Esse arquivo define o formato dos leads simulados. Esses dados alimentam a persona usada pela API. 

export type LeadProfile = {
  name: string;
  role: string;
  segment: string;
  companySize: string;
  solution: string;
  problem: string;
  difficulty: LeadDifficulty;
  visibleObjection: string;
  secondaryObjection: string;
  hiddenConcern: string;
  meetingConditions: string;
};
Campo Como afeta o chatbot
difficulty Define se o lead responde de forma fácil, intermediária ou difícil.
visibleObjection Primeira objeção que pode aparecer naturalmente.
secondaryObjection Objeção revelada depois de alguma investigação.
hiddenConcern Preocupação oculta que não deve ser entregue cedo.
meetingConditions Condições mínimas para aceitar próxima conversa.

10. Checklist De Estudo

  • Entender os estados em GeminiSimulation.tsx.
  • Ler a função send() de cima para baixo.
  • Seguir o fetch("/api/simulate").
  • Ler a validação inicial da rota POST.
  • Entender quando a API usa fallback local.
  • Ler systemInstruction como se fosse o roteiro do personagem.
  • Entender como contents transforma mensagens para o Gemini.
  • Comparar GeminiSimulation.tsx com LocalConversations.tsx.
Resumo final: a interface mostra mensagens e captura texto; a API monta a persona, aplica regras e chama o modelo; os dados do lead definem quem ele é, quais objeções possui e quando aceita avançar.
